# README 质量与本地体验改进设计

> 日期：2026-06-28  
> 状态：已确认，待实现计划  
> 范围：README 生成质量、Provider 默认行为、本地 CLI 使用体验

## 1. 背景

当前 RepoPassport 使用 RepoFacts 生成中文和英文 README。生成器强调事实可靠、简洁和专业，但只有单一文风，默认 Provider 为 Mock，且本地仓库、输出路径、编辑和重新生成流程不够顺畅。

本次改进的目标是：在不削弱证据约束的前提下，让 README 更自然、更实用、更有适度热情；同时让用户可以通过一条简单命令分析本地仓库、生成、预览、编辑或重新生成文稿。

## 2. 目标与非目标

### 2.1 目标

- 默认产出实用、自然、友好且可信的 README。
- 明确区分事实生成与文风润色，润色不得创造新事实。
- 默认使用已配置的真实模型，Mock 仅用于显式测试。
- 支持无仓库参数时分析当前 Git 仓库。
- 让 `--output`、`--open` 和同一运行内重新生成形成顺畅的本地工作流。
- 润色失败时保留事实版 README，避免整个流程失败。

### 2.2 非目标

- 不引入自动评分循环或无限重试。
- 不允许用户注入任意系统 Prompt。
- 不将 API Key 写入配置文件。
- 不改变现有的人工审核和 `--submit` 安全边界。
- 不增加 Web UI、数据库或远程缓存服务。

## 3. 总体方案

采用轻量两阶段生成：

```text
仓库文件
  -> RepoFacts
  -> 事实版 README
  -> 文风润色
  -> 证据过滤与结构检查
  -> 保存、预览、编辑或提交
```

事实版 README 继续使用现有证据约束。新增的润色阶段只改善表达、结构和阅读体验，不增加任何事实。与自动评分重试相比，该方案只增加一次模型调用，行为和成本更可预测。

## 4. 生成组件

### 4.1 事实生成

现有 `generateReadme()` 和 `generateChineseReadme()` 继续负责基于 RepoFacts 生成事实版文稿。事实生成必须：

- 只使用 RepoFacts 中有证据的内容。
- 不编造功能、命令、API、性能数字、许可证或贡献方式。
- 在证据允许时优先生成安装步骤、Quick Start 和典型使用场景。
- 证据不足时生成短而可靠的 README，不填充模板内容。

### 4.2 文风润色

新增独立的 `polishReadme()` 组件。输入为事实版 README、RepoFacts、语言和文风配置，输出为润色后的 Markdown。

润色阶段必须遵守以下不变量：

- 不增加新的功能断言、安装命令、配置项、API、性能数据或许可证信息。
- 保留所有代码块、命令、包名、路径和 API 签名的语义。
- 不删除必要的安全警告或使用前提。
- 不将推测改写成确定性结论。
- 只输出 Markdown，不添加解释或元信息。

润色重点：

- 开头尽快说明项目是什么、解决什么问题、适合谁。
- 改善段落节奏、标题层级和信息顺序。
- 将纯技术列表改写为对用户有意义的收益说明，但不扩大事实。
- 在证据充足时使 Quick Start 更容易复制和执行。
- 删除重复、模板化表达和明显的 AI 腔。

### 4.3 后处理

润色完成后继续执行证据章节过滤，并增加最小结构检查：

- Markdown 代码围栏必须成对出现。
- 文稿不得为空。
- 受保护内容包括代码块、行内命令和 API 签名；润色前后若发生不可接受的变化，则回退事实版文稿。
- 无证据章节继续被移除。

## 5. 文风配置

支持三个固定枚举值：

- `professional`：克制、正式、直接，适合基础设施和企业项目。
- `balanced`：默认值，实用为主，友好热情，允许极少量自然个性。
- `friendly`：更亲切、更具引导性，但仍不得使用夸张营销词。

`balanced` 的目标比例：

- 70% 实用性：用途、安装、Quick Start 和典型场景清楚。
- 25% 热情度：说明项目解决的真实麻烦和实际价值。
- 5% 个性：最多一至两处轻松表达，仅出现在描述性文字中。

所有文风禁止：

- “革命性”“惊艳”“终极”“强大”等没有事实支撑的营销词。
- 网络梗、冒犯性幽默、夸张比喻和强行俏皮。
- 在命令、API、警告和配置说明中使用幽默表达。

## 6. Provider 选择与配置

Provider 按以下优先级选择：

1. 命令行 `--provider`。
2. `~/.repopassport/config.json` 中的非敏感 Provider 配置。
3. 检测到 `OPENAI_API_KEY` 时自动使用 `openai`。
4. 均未配置时停止生成，并输出针对当前操作系统的简短配置指引。

Mock 不再作为默认值，只能通过 `--provider mock` 显式启用。

本地配置允许保存：

- 默认 Provider 名称。
- 模型名称。
- OpenAI-compatible Base URL。
- 默认文风。
- 默认输出目录。

API Key 只能从环境变量读取，不写入磁盘配置。

## 7. CLI 与本地工作流

### 7.1 命令形式

`prepare` 的仓库参数改为可选：

```powershell
repopassport prepare
repopassport prepare .
repopassport prepare https://github.com/owner/repo
repopassport prepare . --style friendly --open
```

省略仓库参数时使用当前工作目录。当前目录必须是有效 Git 仓库，否则给出明确错误。

### 7.2 新增与修复的选项

- `--style professional|balanced|friendly`：默认 `balanced`。
- `--output <path>`：真正将最终文稿写入指定路径；相对路径相对于调用命令时的工作目录解析。
- `--open`：保存后用 `$EDITOR` 打开；未配置 `$EDITOR` 时调用系统默认打开方式。
- `--provider mock`：显式进入测试模式。

现有 `--model`、`--verbose` 和 `--submit` 保持兼容。

### 7.3 审核循环

生成后提供以下操作：

- 保存：接受当前文稿并保存。
- 重新生成：复用当前 RepoFacts，再次生成事实版和润色版，不重新克隆或分析。
- 编辑：先保存草稿，再用编辑器打开。
- 退出：保存运行状态，不执行 Git 写操作。

`--submit` 仍需现有的完整确认文本。重新生成和编辑不会绕过提交确认。

## 8. 缓存与数据流

RepoFacts 在单次 `prepare` 进程内缓存。重新生成只重复文稿生成和润色阶段。

本次设计不要求跨运行缓存，以避免引入缓存失效、Commit SHA 漂移和额外存储管理。现有草稿目录继续保存最终 README、Facts 和证据映射。

## 9. 错误处理

- 事实生成失败：保持现有失败行为并记录运行状态。
- 润色超时、返回空内容、Markdown 结构损坏或违反受保护内容约束：记录警告并使用事实版 README。
- `--open` 失败：文稿仍视为已保存，输出路径和错误提示，不删除文件。
- `--output` 不可写：终止保存并给出目标路径，不回退写入其他隐蔽位置。
- 未配置真实 Provider：在调用模型前退出，给出配置指引，不使用 Mock 兜底。
- 重新生成失败：保留并重新展示上一个有效版本。

错误消息必须经过现有凭证脱敏逻辑。

## 10. 测试设计

### 10.1 单元测试

- Provider 优先级和“Mock 仅显式启用”。
- 三种文风配置的解析和默认值。
- 润色失败、空响应和结构损坏时回退事实版。
- 代码围栏完整性检查。
- 受保护命令、代码块和 API 签名在润色前后保持一致。
- 无仓库参数时选择当前工作目录。
- `--output` 路径解析和写入失败行为。
- `--open` 成功与失败均不影响已保存文稿。

### 10.2 集成测试

- 使用 Mock 分别模拟事实生成、润色成功和润色失败。
- 验证重新生成复用 RepoFacts，不再次克隆和提取。
- 验证 `--submit` 的确认边界未被新审核循环绕过。
- 使用固定 fixture 检查输出包含必要结构、没有禁用营销词。

### 10.3 人工质量验收

选择 3 至 5 个结构不同的真实 JS/TS 仓库，使用真实模型生成 README。由人工分别对以下维度按 1 至 5 分评分：

- 可信度：断言可由仓库证据支持。
- 清晰度：首次阅读能快速理解项目。
- 实用性：安装和 Quick Start 可以直接使用。
- 自然度：语言不像机械模板或明显 AI 生成。

每个维度的目标平均分不低于 4，且不得出现无法追溯的关键断言。该人工验收用于评估输出质量，不自动触发重复生成。

## 11. 验收标准

- `repopassport prepare` 可以分析当前 Git 仓库。
- 未显式指定 Mock 时绝不生成固定 Mock 文稿。
- 默认 `balanced` 文风生效，并可通过 CLI 或配置覆盖。
- 润色不可用时仍能得到事实版 README。
- `--output` 和 `--open` 按设计工作。
- 同一运行内重新生成不会重复克隆或提取 RepoFacts。
- 所有自动化测试通过。
- 真实仓库人工质量验收达到第 10.3 节标准。

## 12. 实施边界

优先复用现有 Provider、RepoFacts、运行记录和草稿目录。新增组件应保持独立：文风配置只描述写作策略，`polishReadme()` 只处理文稿，CLI 层只负责参数、审核循环和文件操作。避免将新逻辑继续堆入已经较大的 `prepare.ts`；实现计划应优先拆出小型、可单测的模块。
